# Дорожная карта StabCam

## Сделано
- Живая гиро-стабилизация (rolling shutter, адаптивный кроп, **точный расчёт «кадр не выходит за границы»**), шумоподавление по времени (+ пространственное и поиск смещения ±2 px), бикубика + резкость, LUT, HLG 10-бит.
- **Горизонт** (выравнивание крена по гравитации): живой режим ограничен запасом кропа, полный диапазон (±45°) в обработке ПОСТ.
- Режим ПОСТ: запись без обработки + лог гироскопа (`.gcsv`, Gyroflow) + лог гравитации + метаданные кадров; обработка на телефоне с предвидением, в **фоновой службе с очередью и уведомлением**.
- Моды `.module`, простой/«Про» режимы, окно обновления, надёжная проверка обновлений.

## Открыто: лаги стабилизации в 4K·60 с включённым OIS
Наблюдение пользователя (OnePlus 15R): иногда заметны «лаги» при STAB в 4K·60 с OIS. Камера 4K60 поддерживает (стоковое приложение снимает), но Camera2 не объявляет `3840×2160@60` в списке режимов для обычных приложений. Приложение всё равно просит 60 fps и получает их (по логу ровные 60 fps), поэтому причины ищем в другом:

| Гипотеза | Как проверяем | Что делаем |
|---|---|---|
| OIS и своя стабилизация «спорят»: OIS уже убрал часть дрожания, а гироскоп видит его целиком, и приложение компенсирует лишнее | Сравнить три ролика: OIS выкл / вкл / вкл + STAB (кнопка OIS, лог `Stab`) | Если OIS-вкл хуже: переключатель «OIS при STAB: выключать» (Настройки → Стабилизация) уже есть; экспериментальный масштаб высокочастотной части гироскопа (`stab.gyroHfScale`); поиск vendor-режима «только OIS» |
| Неровный интервал кадров / пропуски в режиме 4K60 | В логе каждые 2 с: `интервал ср/макс`, `пропусков` | Если пропуски: подбор режима датчика через vendor-ключи (`com.oplus.camera.mode`, `SensorModesInConfig`, `com.oplus.is.sdk.camera.package`) — лаборатория vendor-ключей теперь умеет строки и массивы |
| Нагрев и троттлинг | В логе `тепло N` (0–6 по `PowerManager`) | Адаптивное снижение нагрузки (отключить пространственный шумодав, затем бикубику) |
| Рассинхрон гироскопа и кадров | `stab.timeOffsetMs` ±10 мс, смотреть дрожание | Автоподбор по лог-записи (корреляция гироскоп ↔ движение кадра) |

Просим: снять 3 ролика (OIS выкл, OIS вкл, OIS вкл + STAB) и прислать строки `Stab` из лога.

## Нейросетевое шумоподавление: проверено, для видео на телефоне не подходит
Проверенная модель: **NAFNet-SIDD-width32** (LiteRT-сборка [`litert-community/NAFNet-SIDD-width32-LiteRT`](https://huggingface.co/litert-community/NAFNet-SIDD-width32-LiteRT), на карточке лицензия **MIT**, исходник `megvii-research/NAFNet`). Файл `nafnet_sidd_width32_fp16.tflite`, 62,5 МБ; вход `[1,3,256,256]` RGB 0–1 (NCHW, float32), выход той же формы. По данным карточки: ~46 мс на тайл 256×256 (Pixel 8a, GPU) и ~26 мс (Snapdragon 8 Elite, NPU).

Почему не встроено:
* Кадр 4K = 3840×2160 ≈ **126 тайлов** (без перекрытия), т. е. 3–6 с на кадр; ролик 20 с в 4K60 (1200 кадров) занял бы **больше часа**. Даже Full HD (~32 тайла) дал бы десятки минут, а 720p по качеству бессмысленен для 4K-видео.
* Модель обучена на реальном шуме в разрешении 1:1; прогон по уменьшенной копии меняет статистику шума и работает плохо.
* К тому же 62,5 МБ веса пришлось бы скачивать и держать на устройстве, а проверить результат без самого телефона я не могу.

Решение: нейросеть в видеоконвейер **не включаем**. Остаётся классическое шумоподавление (временное с компенсацией движения + пространственный билатеральный фильтр, в обработке ПОСТ усиленное). Вернёмся к вопросу, если появится видео-модель, укладывающаяся в ~10–20 мс на кадр 1080p (например, облегчённая FastDVDnet-подобная, int8 на NPU) с проверенной лицензией.

## Оси гироскопа
Текущие оси `-y,-x,-z` у OnePlus 15R подтверждены тестом (картинка со STAB стоит ровно). На случай другого устройства есть **автокалибровка** (Настройки → Продвинутые): 4 секунды тряски, сравнение измеренного смещения картинки (мини-кадры 160×90, блочное совпадение) с гироскопом; перебор всех 24 допустимых отображений осей; применяется только при уверенном результате (совпадение ≥ 45% и отрыв от второго варианта ≥ 15%). В журнале каждые 2 секунды выводится угловая скорость по осям устройства (для ручной проверки).

## Идеи на потом
- Нормализация OIS: оценка вклада OIS по расхождению «гироскоп ↔ движение кадра».
- Предпросмотр результата обработки ПОСТ на 5 секунд до полного прогона.

## Разбор исследовательских отчётов (Pixel/iPhone/Samsung/Xiaomi/OPPO)

Принято и реализовано (на устройстве НЕ проверено):
- Сетка rolling-shutter warp 16 строк (`Stabilizer.ROWS`).
- Интринсики по кадрам (`LENS_INTRINSIC_CALIBRATION`, EMA, валидация ±12% фокус / ±5% центр).
- Динамический TNR по ISO: `sigma*sqrt(iso/200)`, 0.012–0.12 (`stab.denoiseAuto`); в POST — по ISO из `.meta.json`.
- CAS-резкость вместо unsharp (алгоритм AMD FidelityFX CAS, MIT).
- Термодеградация: при thermal status ≥3 отключаются denoise и bicubic, возврат при 0..1.
- Калибровка осей теперь оценивает и временной сдвиг гиро (`stab.timeOffsetMs`).
- Приоритет выдержки (`camera.shutterCapMs`, Android 15+, экспериментально).
- POST: камерный NR по умолчанию `minimal` (`post.cameraNr`) — ролик до обработки зернистее.

Отклонено: подмена package name под вендорские whitelist, встроенный нейро-денойз (см. выше), непроверяемые утверждения о значениях вендорских тегов.

## 2026-10-07: тряска на беге
Симуляция (`WalkSimTest`) показала, что при упоре в край запаса выход трясся сильнее входа (×1,18–1,42). Причина — жёсткий упор (излом траектории). Сделано: мягкая граница и больший запас. Остаётся, если на телефоне всё ещё хуже стока: учёт OIS, знак крена (переключатель в меню STAB), синхронизация времени.
